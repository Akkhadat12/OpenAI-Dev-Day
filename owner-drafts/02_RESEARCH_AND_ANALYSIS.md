# OpenAI DevDay 2026 และอนาคตของการมอบหมายงานให้ Agent

ข้อมูลตรวจ 30 กันยายน 2026 เวลาไทย | โครงการ devday-20260930-a7c4 | ข้อเสนอ thesis A

## ข้อสรุปที่รองรับได้

DevDay 2026 สนับสนุนภาพการย้ายจากการใช้ AI เป็นครั้ง ๆ ไปสู่การมอบหมายงานต่อเนื่อง แต่การรับไปใช้จริงจะขึ้นกับผลงานที่ผ่านตรวจ ต้นทุนรวม และขอบเขตสิทธิ์ ข้อความนี้เป็น inference จากชุดผลิตภัณฑ์และสถาปัตยกรรม ไม่ใช่ข้อเท็จจริงเกี่ยวกับการครองตลาด [A01,A02,A04]

Confidence: Medium สำหรับทิศทาง; Low สำหรับขนาดและความเร็วของผลกระทบทางเศรษฐกิจ ไม่ได้ประเมิน probability แบบตัวเลข

## กลไกที่ทำให้แนวทางนี้เป็นไปได้

การมอบหมายงานยาวต้องมีเป้าหมายที่ไม่หายระหว่างรอบ เครื่องมือที่ลงมือได้ feedback ที่ตรวจได้ และสถานะที่กลับมาทำต่อได้ การจัดการระบบเหล่านี้อาจลดงาน infrastructure ที่ผู้พัฒนาต้องทำเอง แต่ไม่ได้กำจัดงานออกแบบกระบวนการหรือการตรวจคุณภาพ [C04,C10]

เมื่อ input จากระบบภายนอกมาเป็น event ได้ งานบางอย่างอาจเริ่มหรืออัปเดตจากความเปลี่ยนแปลง แทนการรอให้คนเขียน prompt ใหม่ทุกครั้ง การส่ง event ซ้ำ การขาดข้อมูล และสิทธิ์ที่เปลี่ยนยังเป็นสิ่งที่ implementation ต้องรับมือ [C08]

การเห็นทั้ง OpenAI, Anthropic และ AWS ทำระบบลักษณะนี้ ช่วยลดความเสี่ยงในการตีความว่าทั้งหมดเป็นเรื่องโมเดลใหม่ของบริษัทเดียว อย่างไรก็ตาม product pages บอกทิศทาง supply มากกว่าความต้องการซื้อจริง จึงใช้ทำนาย adoption โดยตรงไม่ได้ [C09,C10]

## Economics ที่ต้องทดสอบ

ราคา token ที่ถูกลงลดต้นทุนส่วนหนึ่ง หาก workload และคุณภาพคงเดิม แต่ workload ของ Agent เปลี่ยนได้จาก context, retries, จำนวนเครื่องมือ และจำนวนรอบ การเปรียบเทียบที่เหมาะคือ

ต้นทุนต่อผลงานที่ยอมรับได้ = ค่า inference + tools + compute + integration/operation + เวลาตรวจ/แก้ ของงานชุดเดียวกัน หารจำนวนผลลัพธ์ที่ผ่านเกณฑ์

สมการนี้เป็นกรอบบัญชีของผู้วิเคราะห์ ไม่ใช่ข้อมูลทดลอง การใส่ต้นทุน setup ต้องระบุวิธีเฉลี่ย และการเทียบ human-only ต้องรวมต้นทุนภายใต้ขอบเขตเดียวกัน เช่น อย่าเทียบ API bill ฝั่งหนึ่งกับต้นทุนพนักงานทั้งหมดอีกฝั่ง

แยกเวลา wall clock ออกจากเวลาทำงานของคน เวลารอ Agent อาจใช้ทำงานอื่นได้ แต่การสลับงานและ review ก็มีต้นทุน ต้องดูคุณภาพควบคู่กับเวลา

## คำอธิบายคู่แข่งที่ต้องพิจารณา

| คำอธิบาย | สิ่งที่สนับสนุน | สิ่งที่ทำให้ยังไม่สรุป |
|---|---|---|
| Agent platform กำลังเป็นชั้นงานสำคัญ | มี managed execution/context/events หลายราย | ยังไม่ทราบ repeat usage และ unit economics |
| เป็น bundling เพื่อเพิ่ม retention | บริการหลายชิ้นอยู่ใน ecosystem เดียวกัน | Bundling กับประโยชน์จริงเกิดพร้อมกันได้ |
| Workflow เดิมเพียงพอในหลายงาน | งานขั้นตายตัวตรวจผลได้แน่นอน | งานเปิดกว้างบางชนิดต้องปรับเส้นทาง |
| Demo ดูดีแต่ review กิน savings | ความผิดพลาดและข้อมูลขาดมีต้นทุน | ต้องวัดกับ task จริง ไม่อนุมานจากความรู้สึก |

Anthropic เสนอความแตกต่างระหว่าง workflow กับ agent และ tradeoff ด้าน cost/latency เป็น engineering guidance ไม่ใช่ RCT [C12] METR อัปเดตปี 2026 เตือน selection และ measurement problems จึงไม่ควรใช้ผลปี 2025 อ้างว่า Agent ปัจจุบันทำให้ทุกคนช้าลง [C11]

## ใครอาจได้ประโยชน์ และมีความเสี่ยงอะไร

| กลุ่ม | ผลประโยชน์ที่เป็นไปได้ | ต้นทุน/ความเสี่ยง/เงื่อนไข |
|---|---|---|
| คนทำงาน | ลดขั้นตอนเตรียมและรวบรวมงาน | ต้องนิยามเกณฑ์และตรวจผล; ไม่มี job guarantee |
| นักพัฒนา | โฟกัส workflow และ tooling ได้มากขึ้น | Provider coupling, state portability, tool failures |
| ผู้ให้บริการ cloud/runtime | มี workload สำหรับ execution | ไม่ทราบรายได้สุทธิหรือ margin; competition |
| ผู้เชื่อมระบบและผู้รู้ domain | เปลี่ยนข้อมูล/กฎให้ Agent ใช้งานได้ | งาน setup อาจ commoditize; value ต้องพิสูจน์ |
| SaaS/ERP | Data, rules, permissions ยังใช้ในงาน | Interface/seat pricing อาจถูกกดดัน แต่ displacement ยังไม่ยืนยัน |

ทั้งหมดเป็น analysis ไม่ใช่การคาดการณ์ราคาหุ้นหรือรายได้บริษัท [A03]

## ตัวอย่างองค์กรและความย้อนกลับได้

ตัวอย่างสมมติ: Agent อ่านประวัติอุปกรณ์เพื่อจัดหมวดและเตรียมร่าง maintenance notification ไม่ได้อ้างว่ามี Dots–SAP integration พร้อมใช้ การเขียนจริงต้องตรวจ ID, required fields, role authorization และ business rules การเริ่มจากร่าง/ระบบทดสอบย้อนกลับง่ายกว่าการเปิดสิทธิ์เขียนระบบจริง

ค่าเสียโอกาสของการสร้าง Agent คือเวลาที่อาจใช้แก้ master data, ทำ validation ธรรมดา หรือทำ deterministic workflow หากปัญหาคือข้อมูลต้นทางผิด การเพิ่ม autonomy อย่างเดียวอาจไม่แก้ปัญหา

## Scenario ที่ใช้เล่า

| Scenario | เงื่อนไข | สิ่งที่ควรติดตาม |
|---|---|---|
| Base | งานขอบเขตชัด ตรวจผลได้ รับ review ได้ | Accepted-output rate, human minutes, retries |
| Faster adoption | Reliability ดีขึ้นและ integration/review ต่ำลง | Repeat delegated tasks, end-to-end cost |
| Constrained | Review/rework สูง สิทธิ์หรือ connector จำกัด | Exceptions, blocked actions, error impact |

ไม่มีข้อมูลพอให้ probability หรือ adoption deadline จุดยืนยันหรือหักล้าง thesis คือผลลัพธ์จริงที่มีคุณภาพเท่ากัน มิใช่จำนวน Agent ที่เปิดใช้อย่างเดียว

## ข้อเสนอการทดลองในงานจริง

เลือกงานซ้ำที่มีเกณฑ์ชัด ใช้ชุดงานที่เปรียบเทียบได้ สลับเงื่อนไข human-only กับ assisted ตามความเหมาะสม จับเวลาจนผลผ่านตรวจ รวมความผิดพลาดและการแก้ บันทึก task selection และเคสที่ไม่ส่งให้ Agent เพื่อไม่เลือกเฉพาะงานที่มันทำดี

ไม่จำเป็นต้องเริ่มจาก multi-agent หรือสิทธิ์สูง ควรเริ่มขนาดเล็ก แล้วเพิ่มความซับซ้อนเมื่อผลวัดสนับสนุนว่าคุ้ม จุดนี้เป็นข้อเสนอเชิงปฏิบัติของผู้วิเคราะห์ ไม่ใช่ผลทดลองในโครงการนี้
